# Phase 1 Manual Follow-Up — Google OAuth & Environment

Phase 1 adds Google sign-in, a users table, one shared household for the two
partners, a copy-paste invite link for the second partner, DB-backed sessions,
and household-scoped authorization. The code is done; the items below need your
own accounts/values and are **not** committed.

This is a **closed system**: only the Google accounts listed in
`ALLOWED_GOOGLE_EMAILS` can obtain a session. Everyone else is rejected at the
OAuth callback and bounced to `/login?error=not_authorized`.

## 1. Create a Google OAuth client

1. In the [Google Cloud Console](https://console.cloud.google.com/), create (or
   reuse) a project.
2. **OAuth consent screen**: User type *External*; scopes `openid`, `email`,
   `profile`; add **both partner emails** as *Test users* (or publish the app).
3. **Credentials → Create credentials → OAuth client ID**, type
   *Web application*.
4. **Authorized redirect URIs** — add both:
   - `http://localhost:8000/api/v1/auth/google/callback` (local dev)
   - `https://<api-host>/api/v1/auth/google/callback` (production — add once the
     Render API host is known)
   No "Authorized JavaScript origins" are needed (server-side flow).
5. Copy the **Client ID** and **Client secret**.

## 2. Environment variables

### API service (`apps/api`) — new in Phase 1

| Variable | Purpose | Local `.env` | Production (Render) |
|---|---|---|---|
| `GOOGLE_CLIENT_ID` | OAuth client id | from step 1 | set in dashboard (`sync: false`) |
| `GOOGLE_CLIENT_SECRET` | OAuth client secret | from step 1 | set in dashboard (`sync: false`) |
| `GOOGLE_REDIRECT_URI` | must byte-match a registered redirect URI | `http://localhost:8000/api/v1/auth/google/callback` | `https://<api-host>/api/v1/auth/google/callback` |
| `SESSION_SECRET` | signs the short-lived OAuth state cookie | `python -c "import secrets; print(secrets.token_urlsafe(48))"` | auto-generated by `render.yaml` (`generateValue: true`) |
| `FRONTEND_URL` | post-login redirect target + allowed CORS origin | `http://localhost:3000` | `https://<web-host>` |
| `ALLOWED_GOOGLE_EMAILS` | comma-separated allowlist (the two partners) | `you@gmail.com,partner@gmail.com` | same two emails (`sync: false`) |
| `COOKIE_SECURE` | `Secure` flag on the session cookie | `false` (local HTTP) | unset (defaults `true`) or `true` |

Optional tunables with working defaults — set only to override:
`SESSION_TTL_HOURS` (720), `SESSION_COOKIE_NAME` (`fm_session`),
`OAUTH_COOKIE_NAME` (`fm_oauth`).

### API service — unchanged from Phase 0
`APP_ENV`, `DATABASE_URL`.

### Web service (`apps/web`)
**No new variables.** The "Sign in with Google" button links directly to
`/api/v1/auth/google/login`, which `apps/web/next.config.ts` rewrites
server-side to the API using the existing server-only `API_URL`. `API_URL`
only needs to be reachable from the web server (Render's internal
`fromService` hostport is fine).

## 3. Deployment topology note

Google redirects the browser to `GOOGLE_REDIRECT_URI`, which must point at the
**web app's** public host, not the API's — see the cookie-domain note below.
The callback then redirects the browser to `FRONTEND_URL`.

### Production cookie domain — resolved via same-origin proxy

The session cookie (`fm_session`) and the OAuth `state` cookie are set by the
API, `httponly`, with no `Domain` attribute, so the browser scopes them to
whichever host issued the response. In a **split-host** deployment (e.g.
`…-api.onrender.com` + `…-web.onrender.com`), if the API responds directly to
the browser, those cookies land on the API's host and the web app's
server-rendered pages never see them — landing back on `/login` right after a
successful sign-in.

`apps/web/next.config.ts` now proxies `/api/v1/:path*` to the API
(`rewrites()`), and the "Sign in with Google" links point at this app's own
`/api/v1/auth/google/login` instead of the API's origin directly, so both
OAuth hops (login and callback) — and therefore both cookies — stay on the
web app's host.

This still requires one manual step per environment: set `GOOGLE_REDIRECT_URI`
(the API's env var) to `https://<web-app-host>/api/v1/auth/google/callback`,
and add that same URL to the OAuth client's Authorized redirect URIs in Google
Cloud Console.

## 4. Render dashboard

On the `financial-managed-api` service set: `GOOGLE_CLIENT_ID`,
`GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`, `FRONTEND_URL`,
`ALLOWED_GOOGLE_EMAILS` (and optionally `COOKIE_SECURE=true`). `SESSION_SECRET`
is generated automatically. The web service needs nothing new.

The API container now runs `alembic upgrade head` automatically on every boot
(see `apps/api/Dockerfile`), so this revision (`b7f3c1d20a41_auth_and_household`)
and future ones apply on deploy with no manual step.

## 5. Local smoke test

```bash
docker compose up -d postgres
cd apps/api && uv run alembic upgrade head && uv run uvicorn app.main:app --reload
# in another shell:
pnpm --filter web dev
```

Open `http://localhost:3000` → redirected to `/login` → "Sign in with Google" →
consent → back to `/dashboard`. Create a household, click "Invite partner", open
the link as the other allow-listed account → same household as Partner B. A
third / non-allow-listed Google account → `/login?error=not_authorized`.
